# Участие в разработке

## Подготовка окружения

Создайте отдельное виртуальное окружение и установите проект в редактируемом
режиме вместе с инструментами разработки:

```bash
python -m venv .venv
python -m pip install -e ".[dev]"
```

В Windows окружение активируется командой `.venv\Scripts\activate`, в Linux и
macOS — `source .venv/bin/activate`.

## Перед изменением кода

Сначала найдите владельца поведения в
[карте архитектуры](docs/ARCHITECTURE_RU.md). Численные операции относятся к
`src/core`, состояние — к `src/models`, взаимодействие с PySide6 — к
`src/gui`. Не переносите вычисления в обработчики кнопок и не создавайте второе
хранилище координат рядом с графической сценой.

Старые модули-фасады и делегаты `ModePanel` поддерживают совместимость. Если
задача не является намеренным изменением публичного интерфейса, сохраняйте
существующие пути импорта, сигналы Qt, подписи кнопок и формат `.digitizer`.

## Проверка

Полный локальный набор команд:

```bash
python -m pytest -q
python -m compileall -q src tests
```

Для исправления сначала добавьте тест, который воспроизводит ошибку. Для нового
алгоритма проверьте обычный случай, границы допустимого диапазона, неверные
данные и численно вырожденный случай. Изменения интерфейса должны иметь хотя бы
одну проверку состояния или последовательности сигналов без ручного клика.

Особенно внимательно проверяйте:

- логарифмические шкалы и очень большие смещения значений;
- рамки и маркеры чётной толщины с центром между пикселями;
- повторяющиеся X и предел размера выборки в `Curve`;
- инвалидирование калибровки после изменения опор;
- загрузку старого и незавершённого проекта;
- отсутствие изменений живого состояния при экспорте.

## Стиль изменений

- Один модуль должен иметь одну ясную ответственность.
- Предпочитайте небольшие функции с явными входами и результатами.
- Новый код использует канонические пакеты `gui/tables` и `gui/dialogs`, а не
  фасады совместимости.
- Публичное состояние следует читать через свойства, а не через поля с
  начальным подчёркиванием.
- Не смешивайте рефакторинг с изменением поведения без отдельного теста и
  объяснения.
- Не добавляйте в репозиторий `build`, `dist`, виртуальное окружение,
  пользовательские `.digitizer` и экспортированные `.xlsx`.

## Контрольный список изменения

- поведение и границы задачи описаны;
- старые импорты и формат проекта сохранены либо изменение явно обозначено;
- тесты добавлены или обновлены;
- полный набор тестов и `compileall` проходят;
- README и карта архитектуры обновлены, если изменился пользовательский
  сценарий или структура;
- в изменениях нет пользовательских файлов и несвязанных переформатирований.
